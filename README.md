# Retail Demand & Inventory Decision Platform

Forecasts daily demand for **12,196 item-store series** (Walmart M5, California), turns forecasts into weekly
purchase orders under budget, MOQ, case-pack and lead-time constraints, proves the policy against a rule of
thumb in an 8-week replay, and lets planners question and approve plans through a secured AI assistant.

Architecture and design decisions: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

```
M5 data ─► validate ─► features ─► backtest 4 candidates ─► select ─► gate ─► simulate ─► publish (Postgres)
                                                                                              │
React ─► FastAPI (Keycloak JWT, RBAC) ─► LangGraph agent ─► FastMCP tools ─► forecasts / HiGHS optimiser / policy RAG
                                                   └─► human approval (graph interrupt) ─► plan + audit log
```

## Results

Every number below was produced by this repository on 2026-09-16; the raw reports are in [`results/`](results/).

### Forecast accuracy — 3 rolling 28-day backtests (cut-offs d_1857, d_1885, d_1913)

| Model | WRMSSE (mean) | WAPE | Bias |
|---|---|---|---|
| Seasonal naive | 0.752 | 0.889 | −2.3% |
| TSB (intermittent baseline) | 1.085 | 0.750 | −0.1% |
| LightGBM, 28-day lags | 0.585 | 0.737 | −3.6% |
| Two-stage LightGBM (14- and 28-day lag models) | 0.575 | 0.731 | −3.0% |
| Temporal Fusion Transformer, middle-out | 0.583 | 0.733 | −1.9% |
| **Two-stage LightGBM + MinT (selected)** | **0.574** | 0.732 | −2.5% |

- **23.7% lower WRMSSE than seasonal naive.** The pipeline selects the model; nothing is hand-picked.
- Conformal cumulative quantiles on held-out folds: P80 coverage 76.8–80.7%, **P90 88.1–91.1%**, P95 94.2–95.4%.
- Scores cover the California subset over three folds, so they are not directly comparable with the M5
  leaderboard (all 10 stores, one period).

### Replenishment — 8-week day-by-day replay on actual sales, all 12,196 series

| Policy | Fill rate | Stockout item-days | Lost sales | Avg inventory value | Budget violations |
|---|---|---|---|---|---|
| Rule of thumb (days of cover) | 93.1% | 27,000 | $260,078 | $477,781 | — |
| Platform, service level 0.80 | 95.0% | 15,207 (−43.7%) | $188,061 (−27.7%) | $477,197 (−0.1%) | 0 |
| **Platform, service level 0.90** | **95.6%** | **14,245 (−47.2%)** | **$166,053 (−36.2%)** | $526,721 (+10.2%) | 0 |
| Platform, service level 0.95 | 95.4% | 17,503 (−35.2%) | $176,748 (−32.0%) | $569,908 (+19.3%) | 0 |

At 0.80 the platform holds the same inventory as the rule of thumb and still cuts stockouts by 43.7%. Above
0.90 the weekly budget binds, so extra safety stock stops paying back.

**Optimiser:** mixed-integer program solved with HiGHS. On a real 3,049-item store plan it proves optimality in
0.37 s (0.8 s when the budget binds) and returns identical plans on every run. CP-SAT, the first choice, hit its
10 s limit when budgets bound and gave load-dependent plans (see ADR-005). Via the API a full store plan is
created in 979 ms.

| Mode | hit@1 | hit@5 | MRR@5 | p50 | p95 |
|---|---|---|---|---|---|
| BM25 | 0.750 | 0.850 | 0.796 | 0.1 ms | 0.3 ms |
| Dense (BGE-M3) | 0.875 | 1.000 | 0.926 | 37 ms | 47 ms |
| Hybrid (RRF) | 0.825 | 0.950 | 0.870 | 35 ms | 39 ms |
| Hybrid + rerank, top 30 | 0.925 | 0.975 | 0.950 | 2,032 ms | 6,248 ms |
| **Hybrid + rerank, top 10 (default)** | **0.925** | **0.975** | **0.950** | **383 ms** | **428 ms** |

Reranking 10 candidates instead of 30 kept quality identical and cut p50 latency by 81% and p95 by 93%.

### Live stack

- **End-to-end checks with real Keycloak tokens, PostgreSQL and Gemma 4: 18/18 pass**:
  - tampered token → 401; viewer creating a plan → 403; SQL-like input → 422
  - planner cannot approve own plan → 403; approver approves; second decision → 409
  - assistant order pauses for approval, planner cannot resume it, approver can
  - injection refused
- **Load test, 3 minutes, 10 users, one API worker: 255 requests, 0 failures:**

  | Endpoint | Average | p50 | p95 |
  |---|---|---|---|
  | Forecast lookup | 49 ms | 19 ms | 260 ms |
  | Assistant, explain item | 3.6 s | 3.2 s | 10 s |
  | Assistant, policy question | 4.7 s | 3.6 s | 14 s |
  | Assistant, what-if | 5.8 s | 4.8 s | 15 s |

  - Redis retrieval cache hit rate: **89.7%**.
  - Hardware: fanless MacBook Air, CPU inference for BGE-M3 and the reranker, models serialised behind one lock.
    Assistant p95 includes queueing behind that lock; add API workers to scale.
- **Quality:** 40 unit/API tests (60% line coverage; pipeline orchestration is exercised by full pipeline runs),
  ruff and mypy clean.

## Observability

- **Langfuse:** one trace per assistant request, with nested tool calls, policy retrieval (cache hit or miss) and
  the LLM generation with token usage. Enabled when `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_SECRET_KEY` are set.
- **Prometheus `/metrics`:** HTTP latency and errors, optimiser solve time, retrieval cache hits and misses, LLM
  tokens and latency, assistant latency by intent, guard outcomes.
- **Drift:** a Population Stability Index report on key features, latest 28 days vs the training window. Current
  run: all 6 features stable (PSI 0.0006–0.027).
- **Durable approvals:** conversation state is checkpointed in PostgreSQL. Verified by creating a pending
  approval, killing the API, restarting it and approving the same plan.

## Cost and latency levers (measured)

| Lever | Effect |
|---|---|
| Forecasts precomputed nightly | Forecast API p50 19 ms; no model inference on requests |
| Rule-based routing before the LLM | 40/40 routing without LLM calls; lookups never call the LLM |
| Rerank depth 30 → 10 | Retrieval p50 −81%, p95 −93%, quality unchanged |
| Redis retrieval cache | 89.7% hit rate under load |
| Compact tool JSON, top-5 context | ~933 input tokens per answer |
| HiGHS instead of CP-SAT | Simulation 900 s → 109 s; optimal store plans < 1 s |
| CPU-only PyTorch in the Linux image | Removes CUDA libraries (several GB) from the API image |

## Security

- **Authentication:** Keycloak OIDC (authorisation code + PKCE for the web app); the API verifies RS256
  signature, issuer, audience and expiry.
- **Authorisation:** roles viewer < planner < approver. Approval is a separate duty, and a user cannot approve a
  plan they created.
- **Database:** least-privilege roles (`app_write`, `app_read`), parameterised SQLAlchemy queries, Alembic
  migrations. Append-only audit log records actor, action, before/after status and request id.
- **Requests:** rate limits, body size limit, CORS allowlist, security headers.
- **Assistant:**
  - tool allowlist and Pydantic-validated arguments
  - writes only through human approval
  - retrieved text treated as untrusted
  - numeric faithfulness guard; step, token and time limits
- **Supply chain and secrets:** non-root containers, secrets from environment (`.env` locally, AWS Secrets
  Manager in deployment), gitleaks, Bandit, pip-audit and Trivy in CI.

## Run it

```bash
cp .env.example .env              # fill in passwords
make install                      # uv sync
make data                         # validate and build data/processed
docker compose up -d postgres redis keycloak
uv run python -m retail_platform.storage.migrate
make pipeline                     # backtest, select, gate, simulate, publish, index policies
uv run uvicorn retail_platform.api.app:app --port 8000
make web                          # http://localhost:5173 (users: paula / arun / vic, local realm only)
make test && make evals           # tests, routing/guard/retrieval evals
uv run python -m evals.assistant_llm   # needs Ollama signed in (gemma4:31b-cloud) or OLLAMA_API_KEY
uv run python -m evals.e2e_smoke       # live stack checks
make load-test
```

## Limitations

- **Synthetic supply data:** M5 has no supplier, cost or stock data. Lead times, case packs, MOQs, costs and
  shelf capacity are generated with a fixed seed from department and price, using only data before the
  simulation window.
- **Demand:** the simulator treats observed sales as demand. Sales during real stockouts understate demand, the
  standard simplification.
- **Eval sets:** retrieval, routing and guard evals were written for this project and used during development,
  so they are not held-out benchmarks.
- **Not yet done:**
  - AWS deployment files are written (`infra/aws/`) but not yet applied.
  - The GitHub Actions workflows run once the repository is pushed.
